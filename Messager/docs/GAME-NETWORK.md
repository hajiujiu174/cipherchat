# 0.3.21.0 动作游戏通信与同步

依据用户提供的《双人联机小游戏：低延迟通信与同步技术指导 V1.0》落实可测量的低延迟迭代。保留现有认证 TLS 中继和房主模拟，聊天邀请维持原通道；没有把现有协议误称为 WSS，也没有部署 UDP、WebRTC、TURN 或服务端权威游戏 Runner。房主对碰撞、炮弹、得分和胜负裁决，房主作弊与掉线限制仍然存在。

## 已实施

- 游戏输入与状态发送从 100 ms 改为约 40 ms。坦克逻辑仍为 20 ms，羽毛球仍为 15 ms，不通过改移速或改物理 tick 制造“更快”。
- 从机每个固定逻辑步保存输入。快照回显已消费的 client tick，丢弃已确认历史，以完整权威状态为基线重放有界历史；最多保留 32 条，单次预测不超过约 200 ms，超过 250 ms 未获快照时停止前推。
- 坦克仅预测本地移动/转向，直接复用原有 SAT 碰撞与限速实现；炮弹、伤害和比分仍等权威状态。羽毛球预测本地人物与球的视觉状态；得分、回合和比赛结果绝不采用预测结果。可能出现小幅权威校正，不承诺跨平台无误差 Rollback。
- 对手单独插值，本地人物不再固定延迟 100 ms。按近 64 个快照到达间隔的 P90 选择 25–80 ms 缓冲。旧客户端保持兼容。
- 开火、跳跃、挥拍使用单调动作编号，后续输入持续携带累计编号；只应用新编号，避免最新输入合并或个别应用层丢包丢掉短按动作。
- 坦克双方确认同一回合迷宫后不重复传墙体；新回合或未确认时持续发送全量迷宫。缺失全量状态不会凭空猜地图。
- 客户端业务线程和网络层、服务端出站层新增有界实时优先队列；同一玩家/房间/比赛的过期快照及新版连续输入只保留最新项。登录、退出、聊天、文件及控制事件保留可靠语义；给普通流保留公平消费机会、给游戏保留出站空间。
- 客户端与服务端均关闭 Nagle 小包合并；活跃对局缩短网络轮询，空闲后恢复。GUI 收取业务事件在对局期间从 30 ms 调为 5 ms，业务线程空等从 10 ms 调为 2 ms。继续遵守单线程持有同一 SSL 对象的约束。
- 游戏内显示本端回显测得的对局往返、最近样本 P95 和插值缓冲；最多保留 120 个 RTT 样本。数值包含输入周期、房主处理、转发和回包周期，不等于网络 ping，更不能直接称为单程时延。

## 验证与证据

`work/latency-20261021` 保存原指导文件副本、改前源码与测量基线、改后测量、规则回归、隔离双客户端 TLS 对局、文件并发、独立 Linux 服务验证、发布与更新助手证据。

基线和改后均使用隔离的两控制器链路，在每个方向注入 60 ms；还包含 ±15 ms 抖动和按序号丢包的场景。测量的是从机输入到控制器可供绘制的位置变化，不含真实屏幕扫描/显示时延，不代表用户公网 RTT。改前反馈为 205–297 ms；改后结果以 `improved-results.json` 中逐项实测为准。样本数量有限，不据此承诺所有设备或网络的 P95。旧基线短场景只配置了丢包规则，样本不足以实际丢掉每第 33 包；改后压力场景延长以确认真实丢包并验证收敛。

验证覆盖预测与权威移动规则一致、限速/碰墙、历史有界、无效 ACK、短按动作重发与幂等、断线恢复、旧协议兼容入口、原七款游戏、更新通道隔离。真实两个用户跨网对战、校园 Wi-Fi、切网和高负载多房间尚需现场验收。

## 当前边界与后续架构

优先队列实现逻辑调度隔离，底层仍共享可靠 TLS/TCP。已经开始写出的 TLS 帧不可被游戏包打断，TCP 丢包仍可能产生队头阻塞；不能宣称大文件和游戏已实现物理链路完全隔离。独立认证 UDP 服务和权威 Runner、AEAD/DTLS 会话、丢包冗余、拥塞控制、UDP 不可用回退应作为后续完整迁移，不能只加裸 UDP 明文 token 上公网。
